# Домашнее задание 4 — ООП и интерфейсы в Go

Продолжение третьей лабораторной. Вся логика находится в `homework-4/ledger`.

## Структура

| Файл | Назначение |
| --- | --- |
| `ledger/main.go` | Структуры, интерфейс, методы валидации, Ledger и демонстрация |
| `ledger/main_test.go` | Проверки валидации, бюджетов и сохранения данных |
| `ledger/go.mod` | Отдельный модуль `homework-4/ledger` |
| `ledger/budgets.json` | Начальные бюджеты из третьей лабораторной |

## Запуск

Требуется Go 1.22 или новее, сторонних библиотек нет.
Из корня репозитория:

```sh
cd homework-4/ledger
go run .
```

Запускайте из папки `ledger`: программа читает `budgets.json` из текущей папки.
Создавать модуль через `go mod init` не нужно.

Проверка кода из той же папки:

```sh
go test ./...
go vet ./...
```

## Что реализовано

1. Интерфейс `Validatable` с единственным методом `Validate() error`.
2. `Transaction.Validate()` проверяет положительную сумму, непустую категорию
   (строка из пробелов тоже отклоняется) и реальную дату в формате `ГГГГ-ММ-ДД`.
3. `Budget.Validate()` проверяет положительный лимит и непустую категорию.
4. `AddTransaction` и `SetBudget` вызывают методы валидации до изменения хранилища.
   При ошибке объект не записывается; ошибка возвращается вызывающему коду.
5. `CheckValid(v Validatable) error` вызывает `v.Validate()`. В `main` в один
   срез `[]Validatable` помещены оба типа, включая корректные и ошибочные примеры.
6. `LoadBudgets` использует общую валидацию. Все бюджеты проверяются до записи,
   поэтому ошибка в JSON не оставляет частично загруженных данных.

Методы `Validate()` ничего не выводят и не логируют. Сообщения об ошибках выводит
вызывающий код. `CheckValid` только проверяет объект, не добавляя его в Ledger.

В отличие от третьего ДЗ, нулевой лимит запрещён по условию четвёртого.
`SetBudget` теперь возвращает `error`, и вызывающий код обрабатывает его.

## Сохранённая логика Ledger

- Транзакции — расходы, суммы и лимиты заданы целыми рублями (`int`).
- Расход ровно до лимита разрешён; превышение возвращает `ErrBudgetExceeded`.
  Его можно распознать через `errors.Is`.
- Для категории без бюджета расходы разрешены.
- Обновление бюджета сохраняет предыдущие расходы. Если уменьшить лимит ниже
  потраченного, новые расходы будут отклоняться, старые записи сохранятся.
- Категории сравниваются точно, с учётом регистра и пробелов; валидация их не меняет.
- Дубликаты бюджетов в JSON обрабатываются последовательно: последний побеждает.
- Данные хранятся в памяти; JSON не перезаписывается, следующий запуск начинается заново.
- `ListTransactions` возвращает копию среза, отклонённые операции не расходуют ID.

## Демонстрация

Сначала программа показывает результаты `CheckValid` для обоих типов:
две успешные проверки и пять ожидаемых ошибок (сумма, категория, дата, лимит).
Затем выполняются сценарии из третьего задания:

| Операция | Результат |
| --- | --- |
| Продукты: 3000, лимит 5000 | Добавлено, ID 1 |
| Продукты: ещё 2500 | Отказ: превышение бюджета |
| Продукты: ещё 2000 | Добавлено, ID 2, ровно до лимита |
| Транспорт: 800, лимит 1000 | Добавлено, ID 3 |
| Связь: 700, бюджета нет | Добавлено, ID 4 |
| Продукты: 0 | Отказ валидации |
| Увеличение бюджета Продукты до 6000 | Бюджет обновлён |
| Продукты: ещё 1000 | Добавлено, ID 5 |

В конце выводятся пять сохранённых транзакций. Ожидаемые отказы не завершают
программу с ошибкой. Ошибки открытия, чтения или разбора файла останавливают запуск.
